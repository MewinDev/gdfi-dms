# Systems around the workflow

MyLoans sync, the branch list from MyLoans, email and the environment settings.

Last updated: 18 November 2026 (PHT)

- **MyLoans sync.** Find loan is local first: typing searches only the loan files saved in the DMS and never calls MyLoans; the Find loan button calls MyLoans once, by PN, only for a full, valid PN not saved yet (the optional `search` method of the adapter is kept but no screen uses it). The DMS stores only loans that someone opened. When Find loan shows a saved loan, one refresh runs in the background if it was last checked more than 4 hours ago (default; Settings > MyLoans sync, "When a saved loan is found, refresh it from MyLoans if last checked more than this many hours ago"; 0 means never); it never delays opening the loan, skips closed and cancelled loans, waits when the hourly ceiling is reached or MyLoans calls are paused (circuit breaker), and a change it finds raises the usual review ("MyLoans changed"). **Open Items (piece 8, D-053):** a change to a loan or borrower field is an Open Item, one per field, decided by an approver of the loan's branch on the Open Items page (Approve: the DMS takes the myloans value; Reject: it keeps its own; remarks 5 to 500). Loan type, amount, product and release date are decided together, with what the rules would do. Borrower name, CIF and CIN are decided with "Review borrower detail corrections" and block nothing. A newer value supersedes a pending item; myloans putting the DMS value back closes it ("Reverted in myloans"). Every move away from Released (cancelled, not released, inactive, redone) is a status item: Send, Forward and new cash wait until it is decided, and the loan file says why. What Approve does depends on the status, and the card says it first: **Cancelled** closes the loan file (refused while cash is out); **Redone** (the same CIN, myloans' ReplacedBy) moves the same loan file to the new PN and ExternalLoanId, keeping the old PN in its history and its papers, jobs and work (when both loan files already exist and were linked on Related loans, the old one is closed as replaced); **Not released / Inactive** keeps the loan on hold ("On hold: not released in myloans"), blocked but not closed, and when myloans shows it Released again the hold ends by itself ("Reverted in myloans", approvers told). Approvers have **Open Items** in the top menu with the pending count. Branches with no approver of their own go to Unassigned (the Superadmin and All-branches approvers). **Renames** (area, division, company, branch and product names) are lookup data: applied by themselves and listed in Settings, Reference data changes; never an Open Item. Refresh on open when the copy is older than 60 minutes (default; it was 15 before 12 November 2026; a value already saved is kept), never for closed or cancelled loans. **Pause MyLoans calls** (Admin, Settings > MyLoans sync, off by default, audited): when on, the sync (schedule, console command and Run now), the stale refresh and refresh on open make no call; the run log says "MyLoans calls are paused by Admin." and the loan file shows "MyLoans calls are paused by Admin"; Refresh from MyLoans and Find loan for a new PN still call because a person asked. Every sync run is audited. The hourly call count (API 1: Find loan and the refreshes of one loan; the sync reads pages and is not counted) and the circuit breaker are **shared** by every server instance (database tables, one atomic update per call, so the limit holds with several instances or serverless); if the count cannot be written, no call is made ("MyLoans is busy, please try again in a few minutes."). The 60-second answer cache stays per instance. When the hourly limit or the circuit breaker stops a Find loan lookup, the person sees "MyLoans is busy, please try again in a few minutes." (never "not found"). **The sync (piece 7, D-052)** reads only what changed in myloans (API 2, page by page) and replaces the old tiered background refresh. A change run every 30 minutes from the checkpoint; the checkpoint moves only when every page succeeded, so a failed run loses nothing. A daily catch-up at 02:00 Manila reads the last 26 hours again and finds what a run missed. Runs never overlap (a lock). **Nothing is applied by itself:** a change to a loan or borrower field waits as an Open Item (above); a rename is applied by itself and logged. A loan myloans sends twice in one run raises nothing and alerts Admin. Released loans not yet in the DMS are kept (only what the pool card needs) from the branch-pool cutoff (default go-live minus 30 days) and **wait in the branch's LA pool** (piece 10b): one item per PN; its waiting time starts when it entered the pool, not at the release date (shown on the card, with the amount for people who may see amounts); Accept opens Find loan with the PN, and opening the loan file closes the item; it leaves the pool when myloans says it is no longer released; a branch code the DMS does not know goes to the Branch review (Admin's Home says how many released loans wait for a branch) and the loan enters the pool once the branch exists. Every run is in the run log (Settings, MyLoans sync) and the audit log; after 3 failed runs in a row Admin is notified. All of it is in Settings, MyLoans sync (interval, catch-up time and hours, alert threshold, go-live and cutoff dates, Run now, Run the catch-up now). Scheduling: [SCHEDULER.md](../SCHEDULER.md): one entry point, `npm run sync:myloans` or `POST /api/cron/myloans-sync`, for any scheduler; in development an in-app timer (local only). **Replacement (D-051):** a redo is read only from myloans (the same CIN on a new PN, the old copy cancelled or redone, "Replaced by"). The review of the old loan offers that PN, and Admin links it with "Link as replacement", a note (5 to 500 characters) and "I confirmed no payment was made on the old PN" (payment recorded is unknown; the paid / closed source is Phase C). Different branches show "Different branch: {old} → {new}" (never a block). Related loans lists other loans of the same borrower as "Same borrower", with no additional-unit or replacement guess (those tags return with vehicle data from myloans, Phase B); Admin can still link one by hand. Find loan no longer warns about other loans of the borrower (the renewal link is Phase B). The vehicle is not shown (Phase B, Collateral).
- **Account details from MyLoans.** MyLoans is the source of truth for 15 account items (PN, source loan ID, CIN, CIF, borrower name, amount released, released date, loan type, product name and code, branch code and name, area, division and company with their IDs, status ID and name, source). Each loan file keeps them as MyLoans gave them, and every saved copy keeps the whole answer. Area, division and company changes are Minor (the copy is updated); product code and source loan ID are Material; status ID, name and active are Status. Missing product, area, division or company is a warning for Admin, never a blocker. The MyLoans names live only in `live-mapping.ts`; the source query is reference only ([field map](../myloans/field-map.md)).
- **The PN check.** Find loan, the search box, imports and every MyLoans call go through one parser (`parsePn`, lib/pn/format.ts) with the rules in Settings, System, PN format. A wrong PN never reaches MyLoans. Find loan alone also accepts the whole PN without its prefix (the digits only): the prefix is put in front before the same check.
- **Branches from MyLoans.** MyLoans is the source of truth for a branch's code, name, area, division and status (Division > Area > Branch); in the DMS those fields are read-only for MyLoans branches, and DMS-only fields (the usual LTO office, Hide from DMS) stay editable. Branches, areas and divisions are matched by their MyLoans ids first and by code (or name) only when there is no id, so a rename or a changed code is an update, not "new plus missing". **D-054: every branch match uses myloans' BranchID** (the branch list, the loan feed, Find loan and the 10b pool); the code is for display only. A rename or a new code of a branch matched by its BranchID is applied by itself and listed in Settings, Reference data changes; a loan file's branch never changes because of it. **A branch closed in myloans** (a "Closed" review, accepted): its loan files, jobs, inbox items and history stay fully usable for people with access to it; only new pool items stop, and Admin's Home says "Branch X is closed in myloans but has N open items".
  - **Now (no API yet): Import from MyLoans** (Settings, Branches): the tab-separated dump without a header row (division_id, division_name, area_id, area_name, branch_id, branch_code, an unknown column that is ignored and never stored, branch_name, address) or a CSV with a header row (aliases accepted; optional is_active and updated_at). A preview (New, Changed, Unchanged, Not in this file, counts per Division and Area, the access impact, test-looking rows first) and Admin confirms. Rows without a status are Active, except test or unused-looking rows (name with "test" or "don't use", code 999, address "Test Only"), which come in Inactive with "Looks like a test or unused branch" and a suggestion to hide them.
  - **API 4: Branches from MyLoans** (piece 11, D-054; `listBranches()` reads API 4 through the contract client, on the mock until staging access): new, moved, closed, reopened and missing branches go to the same review; renames and code changes are applied by themselves (above). One run a day at about 02:00 PHT through the scheduler entry point (the time and a pause switch are settings), with the advisory lock; the whole list each time, compared branch by branch ("Not in the last list", never deleted). **API 5, products,** is read in the same daily run (also "Read the list from myloans" in Settings, Product classification, which shows when it was last read): a new product is classified by the keywords and the people with "Manage product classification" get "New product: <name>, classified as <Financing/Refinancing>[ by default]"; a rename is logged; a product no longer sent becomes inactive, never deleted. A failed read of either list changes nothing. An unknown branch code in a PN adds an item to the Branch review and triggers at most one small refresh an hour; the lookup is never blocked. Every run is recorded (time, mode, new, changed, unchanged, missing, errors); a failed run changes nothing.
  - **No direct database access.** The DMS never connects to the MyLoans database (MYLOSDB) and never runs SQL against it. The feed is the API through `listBranches()`, or an export file until then. If the MyLoans team can only offer database access, it must be a read-only login on a read-only view or replica, used only inside that one adapter method, never ad-hoc SQL elsewhere in the app.
- **The myloans contract client and mock (piece 6, D-047, D-048).**
  - One client (`lib/myloans/v1`) calls the agreed APIs (1, 2 and the pool mode, 4, 5). It is the same code in both modes: `MYLOANS_MODE=mock` uses the app's own mock, live uses `MYLOANS_BASE_URL`.
  - Every answer is checked against the agreed shapes, and a drift is one plain line naming the field.
  - The mock (route `/api/dev/myloans/...`, its own tables) runs on local or staging, never in production. While it is on, every page shows **"MOCK myloans data"**.
  - Failure switches and scenarios are in Settings, System, "myloans mock" (hidden and refused in production).
  - The contract tests run on the mock in every test run, and by hand, read-only, against myloans staging.
  - Details: [myloans mock and contract](../myloans/mock-and-contract.md).
  - Find loan and Refresh move onto API 1 in piece 10a.
- **Email.** Another channel of the in-app notifications, through Microsoft Graph. One master switch in Settings, System, **Not active** by default. Test mode redirects every email to a test address.
- **Environment.** `.env` for non-secret defaults, `.env.local` for this PC's secrets, hosting settings for production. `APP_ENV` is local, staging or production; production refuses to start with test mode on or mock MyLoans. Details: [Environment variables](../ENVIRONMENT.md).

## Answered by the business (10 November 2026)

1. **Branch, area and division data.** MyLoans has **no API** for these today. The data sits in a MyLoans table (the one the branch export came from). The DB admin may later give a read-only view or an API. **For now the DMS uses Import and Export (CSV)** (Settings, Branches). The DMS still never connects to the MyLoans database directly. The API questions (a stable branch id, an "updated since" filter) are **waiting for the DB admin**; they are not blockers.
2. **Branch after release.** Once a loan is **released**, MyLoans cannot edit it, so a released loan **does not move branch and its PN stays the same**. The DMS only works with released loans. A branch **can** be edited **before** release, but the DMS only captures released loans, so the branch the DMS reads is the **branch at release, and it is final**. The branch code inside the PN is only where the application was opened, so it can differ from the branch at release: that is a fixed difference seen when the loan is first opened, not a later change. The DMS always uses the **branch field from MyLoans** (never the code inside the PN) for access, notifications and Monitoring; the PN code is shown only in the "Opened at X, now at Y" line. The "Opened at X, now at Y" display and the branch-change review stay as they are, but they are **not expected to happen for released loans** and are lower priority; the kit's branch-change samples stay as a test of that safety net.
3. **MyLoans databases.** MyLoans uses **two databases**. **MYLOSDB (LOS)** holds the borrower details and the loan process, and the branch, area and division tables. **MYLMSDB (LMS)** holds the **released computation and the released status**. What the "Sync" and "LMS Sync Status" screens do between them is **not yet confirmed** (it probably moves released loans from LOS to LMS).
   - **Risk:** if the two databases are out of step, a loan can look released in one and not in the other, and the DMS check "valid PN, branch, RELEASED" could refuse a loan that is really released.
4. **The 8-digit column** in the branch export: still **unknown**; it is ignored and never stored.
5. **PN prefix.** The company uses only **GD**, which stands for the company name. The PN format setting stays, with GD as the value.
6. **Finance rules.** Kept as they are for now. The approval bands (the ₱5,000 split between the small and the large approver is a **placeholder**), the carry-over days, the fund-transfer limit, who may change a type and the cash-advance voucher reference are **"Not confirmed. Current values are placeholders."**
7. **Hold transfer.** "Move a hold to another person" is a tick on a role (`holds:transfer`) plus the branch rule: a person with the tick moves a hold only in the branches of their own access, and only to someone who also has access to that branch. **Finance no longer has it**; the built-in **LA Supervisor/Head** role and Admin have it. Settings, Roles warns when an active branch has nobody with the tick.
